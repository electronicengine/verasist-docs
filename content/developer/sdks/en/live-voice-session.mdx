## Prerequisites

- Install `verasist-sdk[voice]` and configure `VERASIST_API_URL`, `VERASIST_API_KEY`, and `WORKFLOW_UUID`.
- Configure and publish the workflow, including its voice models and SDK tool connections.
- Provide an `aiortc` audio track for your microphone or input file, and an audio consumer for the assistant's returned track.
- Ensure signaling and TURN are reachable from the device.

Python uses `LiveSession`; browser TypeScript uses `createDeviceVideoSession` from `@verasist/sdk/video`. Creating the HTTP session alone does not capture a microphone or play audio.

## Create and connect a session

The following example streams an audio file into the call and records the assistant to `assistant.wav`. Set `AUDIO_INPUT` to an existing audio file. For a system microphone, set `AUDIO_INPUT` and `AUDIO_FORMAT` to values supported by your local FFmpeg/aiortc installation, for example a PulseAudio device on Linux. Audio drivers and playback are application responsibilities.

Before running, publish the `sdk_status` schema and connect it to the relevant workflow node using [SDK tools](/developer/sdks/tools). Publication is a setup step, not something you need to repeat for every call.

```python
import asyncio
import os
import socket
from aiortc.contrib.media import MediaPlayer, MediaRecorder
from verasist_sdk import LiveSession, VerasistClient

async def main():
    with VerasistClient(base_url="https://app.verasist.ai") as client:
        session = LiveSession(client, initial_context={"device_name": socket.gethostname()})

        @session.tool(name="sdk_status", description="Read the connected device hostname")
        def status():
            return {"hostname": socket.gethostname()}

        player = MediaPlayer(os.environ["AUDIO_INPUT"], format=os.getenv("AUDIO_FORMAT"))
        recorder = MediaRecorder("assistant.wav")
        recording_tasks = []
        if player.audio is None:
            raise RuntimeError("AUDIO_INPUT must contain an audio track")

        @session.on_track
        def on_track(track):
            if track.kind == "audio":
                recorder.addTrack(track)
                recording_tasks.append(asyncio.create_task(recorder.start()))

        @session.on_transcript
        def on_transcript(event):
            if event["final"]:
                print(event["role"], event["text"])

        @session.on_connection_state
        def on_connection_state(state):
            print("WebRTC:", state)

        try:
            await session.connect(
                workflow_uuid=os.environ["WORKFLOW_UUID"],
                tracks=[player.audio],
                call_context_vars={"locale": "en"},
                ice_timeout_secs=30,
            )
            print("Run:", session.workflow_run_id)
            print("Closed:", await session.wait_closed())
        finally:
            await session.close()
            if recording_tasks:
                await asyncio.gather(*recording_tasks)
            await recorder.stop()
            player.audio.stop()

if __name__ == "__main__":
    asyncio.run(main())
```

For speaker output, consume the received track’s `recv()` frames in your application’s audio playback implementation.

## Session lifecycle

| Method/property | Meaning |
| --- | --- |
| `await session.start(workflow_uuid=...)` | Creates the HTTP session and stores `session_token` and `workflow_run_id`; no media connection yet |
| `await session.connect(workflow_uuid=..., tracks=[...])` | Starts the session if needed, gets TURN credentials, opens signaling and sends the WebRTC offer |
| `await session.wait_closed()` | Waits for call end, connection failure or local close; returns the close payload when available |
| `await session.close()` | Closes local signaling and peer-connection resources; use in `finally` |
| `session.pc` | Underlying peer connection for application diagnostics |

To use an API Trigger node instead, supply `trigger_uuid` instead of `workflow_uuid`. Do not supply both. If you call `start()` explicitly, register all tools first and then call `connect(tracks=[...])` on that same session. Create a fresh `LiveSession` for a new conversation.

`connect()` initiates negotiation; it is not proof that the media path is ready. Observe `on_connection_state`. `ice_timeout_secs` defaults to 30; `None` disables the watchdog. `wait_closed()` can report `ice_timeout` or `ice_failed`. Check TURN reachability and local microphone/speaker configuration when signaling works but audio does not.

## Device tool handlers

`@session.tool(name=..., description=..., parameters=...)` registers a synchronous or asynchronous Python function. Its name defaults to the function name; parameters default to an empty object schema. Arguments are passed as keyword arguments. Return a JSON-serializable value. Handler exceptions are returned as tool errors.

The SDK calls synchronous handlers directly. Move blocking hardware or file operations into `asyncio.to_thread()` inside an async handler, so signaling remains responsive. Validate and constrain device actions in your application.

Only handlers also connected to the **active node** can be called. Moving to a different node removes access to the previous node's SDK tools. A persisted catalog does not substitute for registering the handler in the session.

## Transcripts and voice events

Callbacks are synchronous notifications. Schedule asynchronous work with `asyncio.create_task()` and handle task exceptions in your application.

- `on_transcript`: `{role, text, final}`. User transcripts can be interim; assistant text is final.
- `on_connection_state`: the peer connection's state string.
- `on_voice_event`: `{type, payload}` for `rtf-bot-started-speaking`, `rtf-bot-stopped-speaking`, `rtf-bot-interrupted`, `rtf-user-mute-started`, `rtf-user-mute-stopped`, `rtf-user-turn-started`, `rtf-user-turn-final`, and `rtf-camera-attachment`.

## Send a camera snapshot

Call this helper after the session connects. Supply already encoded JPEG, PNG or WebP bytes, not raw pixels:

```python
from pathlib import Path
from verasist_sdk import LiveSession

async def send_snapshot(session: LiveSession, image_path: str):
    return await session.send_image(
        image_bytes=Path(image_path).read_bytes(),
        mime_type="image/jpeg",
        prompt="Describe what is visible.",
        trigger_response=True,
        timeout=30,
    )
```

The result acknowledges image acceptance; it is not the assistant's answer. The answer arrives through normal transcript/audio events. The backend checks size, dimensions, format and rate limits.

Set `trigger_response=False` when adding context to an already-running response, to avoid requesting a second answer. A compatible multimodal model is required. This snapshot API is not a continuous-video transport.

## Attach an image to a specific user turn

Compatible STT/LLM/TTS and device Gemini Live workflows support turn-bound attachments. After connecting, enable them with `await session.configure_camera_turns(True)`. When `on_voice_event` reports `rtf-user-turn-started`, read `event["payload"]["turn_id"]` and schedule your camera work.

```python
from verasist_sdk import LiveSession

async def attach_camera_turn(session: LiveSession, turn_id: str, jpeg: bytes | None):
    try:
        if jpeg is not None:
            await session.send_image(
                image_bytes=jpeg,
                mime_type="image/jpeg",
                turn_id=turn_id,
                trigger_response=False,
            )
    finally:
        await session.complete_camera_turn(turn_id)
```

Complete the turn even when an image is unavailable. Keep the original turn ID; late images must not be reassigned to another turn. Unsupported servers/workflows reject camera-turn configuration explicitly. Inspect `rtf-camera-attachment` for the outcome.

## Choose voice, video or text

| Conversation | Python | TypeScript | REST |
| --- | --- | --- | --- |
| Voice | `LiveSession(client)` | Run REST + `createDeviceVideoSession` with `autoStartCamera: false` | `run_type: "voice"` |
| Video with voice | `LiveSession(client, mode="video_session")` | Run REST + `createDeviceVideoSession` | `run_type: "video"` |
| Text chat | `client.text_sessions` | `client.textSessions` | `/api/v1/public/agent/workflow/{workflow_uuid}` and `/api/v1/public/agent/runs/{run_id}` |

Voice and video use the published workflow. Enable **Video session** in workflow settings and select an image-capable visual model before creating a video session. Allow camera, screen, or both. Existing voice and text sessions keep their own mode; create a new session to use video.

## Create a live session with REST

Keep your organization API key on your application server. Use a workflow UUID:

```bash
curl -X POST 'https://app.verasist.ai/api/v1/public/agent/workflow/YOUR_WORKFLOW_UUID' \
  -H "X-API-Key: $VERASIST_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"run_type":"video","initial_context":{"locale":"en"}}'
```

Alternatively, use `POST /api/v1/public/agent/{uuid}` with the API Trigger node UUID. The response includes `session_token`, `workflow_run_id`, `expires_at` and optional `scheduling`. A queued start can return HTTP 202; keep the same session and wait for readiness instead of creating another one. The scheduling kind is `video` for video, `webrtc` for voice, and `chat` for text.

REST creates the session. Audio travels over WebRTC and visual frames travel over signaling; the HTTP response alone does not activate a camera. Use [Runs API reference](/api-referansi/runs/trigger-workflow) for request fields and Try it.

## Browser voice and video

Use an SDK build that exports `createDeviceVideoSession`. If your installed package predates this helper, use the existing `VideoSession({signalingUrl, iceServers, autoStartCamera})` constructor with `wss://YOUR_API_HOST/api/v1/ws/device/signaling/SESSION_TOKEN` and TURN credentials from `GET /api/v1/public/agent/runs/{session_token}/turn-credentials`. Never put the organization API key in the signaling URL.

Create the token on your server using the SDK, then return only that token to your authenticated browser:

```typescript
import { VerasistClient } from "@verasist/sdk";

const client = new VerasistClient({ baseUrl: "https://app.verasist.ai" });
const result = await client.startRunByWorkflow(workflowUuid, {
  body: { run_type: "video" },
});
// Return result.session_token to the authorized browser. Keep the API key server-side.
```

In your browser, provide an audio element and a muted, inline video element:

```typescript
import { createDeviceVideoSession } from "@verasist/sdk/video";

const session = await createDeviceVideoSession({
  apiBaseUrl: "https://app.verasist.ai",
  sessionToken, // Token received from your application server.
});
session.addEventListener("audio", (event) => {
  audioElement.srcObject = new MediaStream([(event as CustomEvent<MediaStreamTrack>).detail]);
});
session.addEventListener("stream", (event) => {
  previewElement.srcObject = (event as CustomEvent<{stream: MediaStream | null}>).detail.stream;
});
session.addEventListener("status", (event) => console.log((event as CustomEvent).detail));
await session.connect();
// Bind these calls to your application buttons:
// await session.startVideo("screen");
// await session.stopVideo(); // Voice continues.
// session.close();
```

For voice, create with `run_type: "voice"` and pass `autoStartCamera: false` to the browser factory. Do not call `startVideo` for a voice session. For an embed-authorized deployment, continue using `createVideoSession({apiBaseUrl, embedToken})` from the same SDK entry point.

Use HTTPS or localhost. Camera starts once after video capabilities are ready. Camera permission rejection reports an unavailable status without ending voice. Screen sharing must start from a user action and depends on browser support. The factory fetches TURN credentials with the short-lived token; HTTP 503 falls back to STUN, while invalid/expired tokens fail. `close()` releases microphone, camera/screen, peer connection and signaling resources. Browser autoplay may require a user action to play assistant audio.

## Python continuous visual observations

Your application owns camera capture or screen snapshots; the SDK does not open a camera automatically. Create `LiveSession(client, mode="video_session")` before calling `connect`. After connecting, use the application's JPEG bytes:

```python
capabilities = await session.video_capabilities()
if capabilities["enabled"] and capabilities["allow_camera"]:
    await session.configure_video("camera")
    await session.send_video_frame(jpeg_bytes, "image/jpeg")
    # Send further frames no faster than capabilities["interval_seconds"].
    await session.configure_video(None)  # Stop images; voice continues.
```

Use `configure_video("screen")` for application-owned screen snapshots when allowed. The SDK associates frames with the current source and generation. `send_video_frame` rejects sending after video is stopped. `on_voice_event` receives `video-status` events, including analysis and error details. If `capabilities["record_video"]` allows recording, your encoder can send consecutive `send_video_recording_chunk(data, sequence, mime_type="video/webm")` chunks. Voice and video recording follow the workflow settings.

For text creation, execution, message revisions, streaming and closing, see [Text sessions](/developer/sdks/text-session). Text does not use a live-session token or WebRTC.


Start voice, video and text through the existing run endpoint with `run_type: "voice" | "video" | "text"`. Omitting the field preserves telephone/channel execution. Text creation requires a UUID `request_id`; message and close operations use `/api/v1/public/agent/runs/{run_id}`. Legacy session addresses remain compatibility aliases.
